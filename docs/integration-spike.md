# 기존 ROS·시뮬레이터 재사용 검증

담당: yumina0616, 웹 연결 협업: JH-9568. Issue: [#2](https://github.com/yumina0616/ai-championship-2026/issues/2).

## 전제 재확인 (2026-09-15)

착수 전 가정이었던 "팀원에게 가상 차량 제어·센서 수신 기존 코드가 있다"는 실제로 확인되지 않았습니다. 따라서 이 문서는 "기존 코드 검증"이 아니라 "실행 엔진을 무엇으로 새로 구성할지"에 대한 spike로 범위를 조정해 진행했습니다.

## 시도 1: ROS2 + Gazebo (옵션 A, 서버 재사용/신규 구축)

yumina0616 PC에는 WSL2 Ubuntu-22.04에 ROS2 Humble과 Gazebo Harmonic(gz-sim 8.14.0, `ros_gz_bridge` 포함)이 이미 설치돼 있어 여기서 최소 스파이크를 만들어봤습니다.

- 구성: `gz-sim` world에 차량(박스, footprint는 `examples/scenarios/reverse-bay.v1.json`의 `wheelbase_m=2.6, front_overhang_m=0.9, rear_overhang_m=0.9` 그대로 사용) + 벽 1개 + 전방 1-ray 라이다(`gpu_lidar`, pose는 fixture의 `sensor.pose_vehicle` x=1.3 재사용).
- 제어 방식: Gazebo 자체 차량 동역학 대신, `docs/contracts.md`의 rear-axle bicycle model을 Python(`gz-transport13`, `gz-msgs10`)으로 직접 적분하고 `/world/<world>/set_pose` 서비스로 결과 pose를 반영(물리 엔진의 타이어 모델에 맡기지 않고 우리 수식을 그대로 검증).

**실측 결과 (headless, WSL2, 2026-09-15):**

| 단계 | 명령 | 결과 | 기대와 일치 |
| --- | --- | --- | --- |
| reset | car→(0,0,0), wall→(6.5,0,0.5) | pose=(0,0,0) | O |
| 초기 센서 | - | front_lidar=5.100m | O (6.5-0.1-1.3=5.1 계산과 일치) |
| 직진 2s | speed=+0.8, steer=0 | x=1.600, y≈0, yaw≈0 | O (0.8×2=1.6) |
| 직진 후 센서 | - | front_lidar=3.500m | O (5.1-1.6=3.5, 장애물 이동 없이도 차량 이동만으로 갱신됨) |
| 좌회전 2s | speed=+0.5, steer=+0.3rad | y=+0.058, yaw=+0.119 | O ("왼쪽 양수" 부호 확인) |
| 후진 1.5s | speed=-0.5, steer=0 | x 2.598→1.853로 감소, yaw 고정 | O (진행방향 반전, yaw 불변) |
| 장애물 이동 | wall을 차량 앞 2.0m로 이동 | front_lidar=0.613m | O (기하 재계산, 연출 아님) |

**발견한 문제:**

1. WSLg의 GPU 패스스루(Intel iGPU, `libd3d12core.so`/`libigd12um64xel.so`)에서 Ogre2가 셰이더 컴파일 중 **segfault로 죽음**. `LIBGL_ALWAYS_SOFTWARE=1` + `GALLIUM_DRIVER=llvmpipe`(소프트웨어 렌더링)로 전환해야 안정적으로 뜸.
2. 소프트웨어 렌더링 상태에서 실시간성(1 sim-second를 1 wall-second 안에 계산)을 장담할 수 없고, 이를 검증하려면 배포 환경(클라우드 VM의 GPU 유무)까지 별도로 맞춰야 함 — 제출까지 남은 기간 안에 안정화를 보장하기 어려움.
3. set_pose 서비스 호출 중 1회 transient 실패 관찰(명령을 빠르게 연속 전송할 때) — 재시도/ack 설계가 필요했을 것.
4. 재사용할 기존 코드/모델/에셋이 전혀 없어 "재사용"의 이점(개발 시간 단축)이 사실상 없고, ROS2/Gazebo 생태계 전체(메시지 타입, 빌드, 배포 이미지)를 처음부터 새로 구성해야 하는 부담만 남음.

## 결정: 옵션 B — 브라우저(TypeScript) 내 엔진 직접 구현

**선택한 실행 엔진/버전**: 별도 물리 엔진 프로덕트를 쓰지 않고, `docs/contracts.md`의 rear-axle bicycle model과 ray-box 거리 센서를 TypeScript로 직접 구현한다. 위 ROS2/Gazebo 스파이크에서 실측으로 검증한 수식·부호 규칙을 그대로 이식한다.

**실행 위치와 이유**:

- 일정: 재사용 가능한 기존 코드가 없는 상태에서 ROS2/Gazebo를 제출 마감(9/20)까지 5일 안에 안정화하는 것은 리스크가 크다(위 GPU 렌더링 문제, 배포 환경의 GPU 유무 불확실성).
- 확장성(장기 목표와의 정합): 이 프로젝트는 다수 사용자의 주차 시도 데이터를 모아 정책을 학습시키는 참여형 데이터 수집을 목표로 한다(`docs/data-learning.md`). 옵션 A는 사용자 세션마다 서버에 Gazebo 프로세스를 떠야 해 동시접속이 늘수록 서버 비용/복잡도가 선형으로 증가한다. 옵션 B는 물리·센서 계산이 각 사용자의 브라우저로 자연히 분산되고, 서버는 정적 호스팅과 (동의한) Episode 저장만 담당하면 된다. 즉 이번 선택은 단순 시간 부족에 따른 타협이 아니라 제품의 핵심 목표에 구조적으로 더 맞는 결정이다.
- `docs/architecture.md`가 명시한 대로 A/B를 동시에 주력으로 만들지 않는다 — B 하나로 확정한다.

**그대로 재사용하는 코드**: 없음(엔진 레벨). 단, 스파이크에서 검증한 bicycle model 수식·좌표 부호·ray-box 거리 계산 로직은 그대로 TypeScript로 옮겨 재사용한다.

**웹 연결 방식과 세션 수명**: 네트워크 왕복 자체가 없다 — 엔진이 브라우저 탭 내부에서 동작하므로 "연결"은 클라이언트 프로세스의 생명주기와 같다. 세션 분리는 탭/사용자 단위로 자동 보장된다. 서버는 (1) 정적 자산 호스팅, (2) 동의한 Episode 업로드/공유 맵 저장(#13), (3) 후속 학습된 모델 inference만 맡는다(아래 미결 사항 참고).

**고정 dt, reset/step 가능 여부**: 가능. `requestAnimationFrame`과 분리된 고정 dt(0.05s) 누적기(accumulator) 패턴으로 구현할 계획(렌더 FPS가 물리 시간에 영향을 주지 않도록 `architecture.md` 원칙 준수). reset/step은 JS 함수 호출이라 엔진-자체 reset으로 구현.

**로컬/배포 실행 명령과 실측 지연**: 아직 TS 코드 없음 — #5(차량)·#7(센서)에서 실제 구현 후 프레임타임 실측.

**지원하지 않는 기능과 제출 영향**: Gazebo의 정교한 타이어 동역학, 환경별 센서 노이즈 모델(레이트레이싱 기반 occlusion 등)은 제외. 원래 계약도 "저속" kinematic model + 무잡음 기준 ray-box 센서를 1차 목표로 하므로(`docs/contracts.md`) 제출 범위에 실질적 영향은 적다.

**코드/모델/에셋 공개 범위와 프로젝트 라이선스 결정**: 외부 엔진/에셋을 가져오지 않으므로 라이선스 검토 부담이 단순해진다. 저장소 자체 코드로 공개 범위를 정하면 된다(프로젝트 라이선스는 여전히 팀 합의 전).

**합의자/날짜/PR**: yumina0616, 2026-09-15, 이 Issue의 PR에서.

## 미결 사항 — #9/#11에 영향

엔진이 브라우저(JS/TS)로 확정되면서, 학습된 정책(#11)을 **어디서 추론할지**가 새로운 결정 지점이 됩니다:

- (a) 정책도 브라우저에서 추론 (예: ONNX Runtime Web, TensorFlow.js) — 서버 의존도가 가장 낮고 옵션 B의 확장성 이점을 그대로 유지하지만, 학습 프레임워크/모델 크기가 브라우저 추론에 맞게 제약된다.
- (b) 물리/센서는 브라우저, 정책 추론만 서버 API로 호출하는 하이브리드 — 모델 선택 자유도는 높지만 "마스코트 운전" 모드에서만 네트워크 왕복이 다시 생긴다.

지금 결정하지 않고 #9(기준 제어기)·#11(학습) 착수 시점에 모델 크기/프레임워크가 정해지면 근거를 남기고 결정합니다. `docs/architecture.md`의 "학습 경계" 절과 함께 갱신 필요.

## 검증 순서 (기록용, 수행 완료)

1. 차량 1대와 벽 1개를 실행하고 reset 직후 pose를 기록합니다. — 완료(위 표)
2. 낮은 속도로 직진·좌/우 조향·후진·정지를 각각 실행합니다. — 완료(직진·좌회전·후진, 우회전/정지는 대칭이라 생략)
3. 벽을 이동시켜 센서 수치가 바뀌는 원시 측정값을 기록합니다. — 완료
4. 웹 버튼에서 command를 보내고 pose/센서 결과를 화면에 표시합니다. — 해당 없음(옵션 B 확정으로 네트워크 왕복이 사라짐). 브라우저 내 호출 왕복은 #5/#7에서 실제 UI와 함께 확인합니다.
5. 연결 끊김·reset·두 세션을 검사합니다. — 해당 없음(탭 단위 격리). 서버에 올리는 Episode 업로드 동시성은 #13에서 별도 확인.
6. headless 또는 선택한 호스팅에서 같은 경로가 가능한지 확인합니다. — 해당 없음(정적 호스팅이면 기본 충족, #4/#15에서 실제 배포로 재확인).
7. 로그/영상/commit과 실패한 항목까지 Issue에 첨부합니다. — 이 문서 + Issue #2 댓글에 기록.
